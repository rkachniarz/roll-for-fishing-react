# Roll for Fishing: notes for Claude

A pixel-art fishing game for phone and desktop: cast, watch the bobber, strike when it splashes, and roll a d20 to land
the catch. PixiJS for the scene, plain DOM for the UI, no framework, no build step to run it. See README.md for the
file map.

**Not here:** reasons in full (`docs/decisions.md`; a bullet here names the trap and cites the decision), plans
(`DEV_PLAN.md`), the file map (`README.md`).

## Development plan

**Read `DEV_PLAN.md` before starting work.** It holds the open questions and the remaining phases, with tickboxes. Tick
tasks off as they land. It has two tracks (D105): development, and creative work (art, writing, sound, `CR-n`).
**Creative work never blocks development:** when a task needs art or text that isn't there, build it with a
placeholder (squares and triangles, a plain sentence, a stand-in rule in REVIEW.md) and list the placeholder under the
`CR-n` task that will replace it. The rest is in `docs/`, read when a citation calls for it, since code comments cite all of these
by number:

- `docs/areas.md`: **where to look.** Each area of the game (the sky, the pool, the page…) with its files, tests, the
  decisions and requirements behind it, the sections of other docs about it, and the traps below that touch it.
  Generated by `npm run areas` (D184); read the area before working in it. A new source file goes into an area in
  `tools/areas.mjs`, and after changing decisions or docs, `npm run areas` brings the index up (a test checks both).
- `docs/decisions.md`: the decision log, `D1` onwards. Record new decisions there rather than silently changing
  requirements.
- `docs/spec.md`: the vision, requirements (`R1.1`–`R21.1`) and catalogues (`§C.1`–`§C.6`).
- `docs/history.md`: finished phases, task by task, with what was measured.
- `docs/events.md`: how to write an event, and every word of the format (D84).
- `docs/art.md`: how the art is made with the owner (D90): style rules, sizes, trials, drawings in MS Paint. Read it
  before changing any art.
- `docs/placeholders.md`: every placeholder in the content, generated by `npm run content` (D124). The owner loves
  placeholders: make them freely for any content, and **mark every one** (`"placeholder"` in a content file,
  `placeholder: true` in an event, `PLACEHOLDER_UI` in `src/strings.js`), so they can be told apart.
- `docs/REVIEW.md`: guesses and calls Claude made that the owner hasn't checked yet. **Add to it** whenever you pick a
  number, write content, or decide something the owner didn't (D76); the owner deletes items once settled, so an
  item only asks (D182). **Never keep knowledge only there:** sources, references and how sure a pick is go in
  `docs/sources.md`, a number's reason beside it in the code or content, measurements in `docs/history.md`, loose ends
  and things never seen working in DEV_PLAN.md ("Known gaps"). Code never cites REVIEW.md.
- `docs/sources.md`: where the real-world facts (FishBase, the Red List, the wind rose, reference photos) and
  Claude's numbers came from, and how sure each is (D182). Read the area's section before changing it.
- `docs/ideas.md`: the owner's loose ideas for events, people and the story, not requirements yet. Read it before
  writing events or content; the engine work they need is in DEV_PLAN.md.
- `docs/PORTING-NOTES.md`: what to port from the React prototype (tag `legacy-prototype`; read old files with
  `git show legacy-prototype:src/Data/weather.js`) and the lessons it taught.
- `docs/town-questions.md`, `docs/brainstorm-2026-11-14.md`, `docs/ideas/items.md`: dated records of questions and

- `art/README.md`: what the `art/` folder holds (drawings and exports for Paint); `assets/CREDITS.md`: the pictures

Pushing `master` publishes the game to GitHub Pages once `npm test` passes (D91, D133):
https://rkachniarz.github.io/roll-for-fishing-react/ (and `art.html`). Push only when the owner asks.

A phase ends with `npm test` and `npm run verify` passing, then `npm run build` (`npm run check` does all three), then a docs refresh: DEV_PLAN.md
(ticks, "Where things stand"), history.md, this file, README.md, and `npm run prompts`.

**The docs are the only source of truth besides the code**, and Claude writes all of it. They have two jobs: when
working next to something that exists, Claude must (1) know there is knowledge to be found, and (2) know where to
look for it. Each kind of knowledge has one home (D182); nothing lives only in a file that is meant to empty.
**"Doc review"**, when the owner asks for one, means looking first for whatever gets in the way of those two jobs: a
doc drifting from its purpose, knowledge in the wrong home or only in a file meant to empty, pointers that lead
nowhere (to a deleted item, a renamed file, a retired decision), code with nothing pointing at the decisions behind
it, and the same fact in two places that disagree. Wording and tidiness come after. `test/docs.test.js` catches the
mechanical half (D183); a doc review is for the rest, which only reading finds.

**Prompt count:** `npm run prompts` records how many prompts the owner has given per session in `docs/prompts.json`
(counts and dates, never the text), so the number survives Claude Code deleting old transcripts. Run it at the end of
every phase, and whenever the owner asks how many prompts it has taken; it never drops a session already recorded.

**UI: when in doubt, copy World of Warcraft (D29).** If you aren't sure how WoW does something, ask the owner instead
of guessing.

**Strings the owner changes:** when text in `src/strings.js` or `content/` changes without Claude changing it, the
owner did it on purpose (D85). Keep it; don't put Claude's wording back.

```bash
npm install
npm run dev     # http://localhost:8001 - must be served, ES modules don't load over file://
npm run content # check content/ and regenerate src/generated/content.js (run after editing content)
npm test        # unit tests (node:test): rng, dice, content, weather, time, fish, the game engine, the docs' pointers (D183)
npm run verify  # browser checks in headless Chromium; starts its own server on :8123
npm run verify strike   # only the checks whose label contains "strike"
npm run build   # -> dist/artifact.html, the single-file copy for claude.ai
npm run check   # test, verify, build in turn, stopping at the first failure
npm run sprite export bobber   # a sprite as art/bobber.png to draw on; `import <file> [keys=icons] [bg=ffffff]` reads one back
npm run photo-icon <photo> name=icon-fish-<id>   # a first-draft 32×32 icon from a photo; follow the photo-to-icon skill
npm run cutout <photo> [flip=Name]   # cut the subject out of a busy photo, onto magenta (first: npm run cutout setup)
npm run commons search <slug> "<query>"   # Wikimedia Commons pictures on a contact sheet; then commons fetch <slug> <n> name=<Name>
npm run sim [casts=500 games=20 class=rogue-fisher strike=250..900 perks=first|passive|active]   # balance: seeded games per class (9.1)
npm run planks [pine|oak]   # the light theme's tabletop tile, from docs/design/refs/, into styles.css (D143)
npm run obsidian            # the dark theme's obsidian tile, drawn as code, into styles.css (D145)
npm run map                 # the map's paper and outline, from docs/design/map/, into src/generated/map-paper.js (D161)
npm run areas   # rebuild docs/areas.md, the index of where to look (D184); a test fails while it is behind
npm run names   # the owner's name lists (docs/names/*.csv, local only) into content/names/, then npm run content (8.13)
npm run prompts # record the owner's prompts per session in docs/prompts.json, and print the total
# http://localhost:8001/art.html   the art sheet: trials, fish that swim, the painted spots by season, every sprite and icon enlarged;
#   each section folds and builds when opened; #seed=N, #open=all (a # not a ?: serve redirects art.html and drops a ?)
# http://localhost:8001/?ph          placeholder text marked with a ° (D124)
# http://localhost:8001/?dev       dev bench; ?seed=N seeds a new game (a save wins); ?wait=MS fixes the bite delay
# http://localhost:8001/editor.html   the content editor (7.5): forms from the schemas, saving into content/ (Chrome, Edge)
```

## Things that look arbitrary but are not

These are the traps that cross every area: break one and something goes wrong far from where you are. A trap that
belongs to one area is a `Trap:` line in the header comment of the file where the mistake would be made, and
`docs/areas.md` lists each area's traps (D185): read the area before working in it. A new trap goes beside its code.

- **Generated files are never edited by hand.** `src/generated/content.js` (D43, D72): edit `content/`, then
  `npm run content`; a test fails if the two disagree. Its text is keys (`fish.pike.name`), read with `t()` from
  `src/strings.js` (D46). Also generated: `docs/placeholders.md` (`npm run content`), `docs/areas.md`
  (`npm run areas`), `src/generated/map-paper.js` (`npm run map`), and the patterns in `styles.css` (`npm run planks`,
  `npm run obsidian`).
- **Content ids are permanent (D44).** Never rename or delete one; set `"retired": true` instead.
- **`castLine` in `src/engine/game.js` rolls everything on the line when it goes out (D63),** hidden, and returns a
  `checkpoint` to save while the cast is in progress: buff charges spent, nothing else (D74). Saving the full state
  mid-cast would let a reload reroll the line. So `src/main.js` saves the checkpoint while a cast is in progress and
  the full state otherwise, and the dev bench changes the state only between casts; its game value overrides and
  `?wait` are `extra` sources passed to the engine, never saved.
- **Nothing that affects an outcome may use `Math.random` (D4).** Draw from a stream: `deriveSeed(seed, 'label')`, one
  label per consumer, so extra draws in one system never shift another. Cosmetic randomness in the scene uses the
  `scenery` stream for the same reason (it keeps screenshots reproducible).
- **The save holds every random stream's position (D53),** not just the seed. Take dice with `diceFrom(state)` and
  store `commit()` in the next state; never create a stream from the seed mid-game. Tend the pool (`tendPool` or
  `tended`, `src/engine/pool.js`) before `diceFrom`, or the commit writes the old positions back over the pool's
  draws. A new stream means a new `SAVE_VERSION` and a migration that derives it (`STREAMS` in
  `src/engine/state.js`), or an old save has no position for it.
- **`src/dice.js`: the dice are separate named functions on purpose (D5).** `roll20`, `roll2d6`, `roll100`… Don't
  merge them into a generic `roll('NdM')`. A new die is a new function in the same style.
- **`src/engine/` takes `now` as an argument and never reads a clock (D7).** That's what lets the tests play a whole
  cast in a few lines.
- **Pixels are whole and never scaled.** The scene's scale is a whole number of *device* pixels, not CSS pixels (D10,
  `scene.fit`): at devicePixelRatio 2.625 a whole CSS multiple still smears. Sprites are never scaled at runtime
  (R7.3): depth uses separate sprites per band (`BOBBER` / `BOBBER_FAR`), and positions are rounded every frame. The
  scene is wider than the play area (D93): everything the engine places lives in the `play` container in 256×256
  coordinates, so convert pointer positions with `scene.toScene` / `scene.toClient`, never by dividing by 256.
- **Luck is read through `luckOf(state)` (`src/engine/events.js`),** which adds the marimo's +1 (D150). Reading
  `state.character.luck` skips it.
